Quant Dashboard

퀀트 수집 작업이 제때 돌았는지 읽기만 하는 상태판

개요

한 서버에서 도는 여러 퀀트 프로젝트의 자동 수집 작업이 오늘 제때 실행됐는지, 서버에 접속하지 않고 한 화면에서 확인하려고 만들었습니다. systemd, Docker, 각 프로젝트가 남기는 파일을 읽기만 해서 상태를 OK / WARN / UNKNOWN / FAIL로 판정하고, 감시 대상에 영향을 주지 않는 것을 가장 중요한 요구사항으로 삼았습니다.

CASE 01Quant Dashboard개인

휴장일·동시호가의 정상적인 공백을 장애로 보지 않도록 날짜 분류를 판정 앞단에 두었다

  1. 날짜 분류5가지 중 하나로 분류
  2. 할 일 결정일정표와 비교
  3. 시간대 판정정규장·동시호가·애프터
  4. 단계 부여OK/WARN/FAIL
  5. 미확인 처리범위 밖은 UNKNOWN
P 문제

같은 '데이터가 안 들어옴'도 거래일 장중이면 장애이고 휴장일이나 동시호가(15:20~15:30)면 정상입니다. 개발 중 이를 장애로 잘못 판정한 오탐이 세 번 나왔습니다(커밋 이력 기준).

A 분석
  • 시간대마다 임계값만 따로 두는 방법은 오늘이 어떤 날인지 모르면 '해야 할 일' 자체를 정할 수 없어 제외했습니다.
  • 하루를 거래일·휴장일·주말·시간 변경일·미확인으로 먼저 분류하는 방법을 선택했습니다. 확인된 기간(2026년) 밖은 UNKNOWN으로 둡니다.
  • 정규장은 틱이 120초 넘게 없으면 WARN, 300초 넘으면 FAIL로 두고, 15:20~15:40은 판정을 보류했다가 애프터마켓 600초 기준으로 넘깁니다.
A 실행
  • 달력을 TRADING / HOLIDAY / WEEKEND / SHIFTED / UNKNOWN으로 분류하는 모듈을 만들었습니다.
  • 휴장일에 정상 종료된 작업은 '결측'이 아니라 정상 종료로 표시하게 했습니다.
  • 달력 분류와 시간대별 판정을 단위 테스트로 고정했습니다.
R 결과 코드로 확인

휴장일·동시호가·마감 후처리 중 하트비트 단절, 세 가지 오탐을 각각 수정하고 테스트로 고정했습니다. 오탐이 줄어든 정도를 수치로 측정하지는 않았습니다.

CASE 02Quant Dashboard개인

감시자가 감시 대상을 느리게 하지 않도록 읽기 전용과 수정 시각 확인만 쓰도록 했다

  1. 명령 요청외부 명령은 한 곳으로
  2. 허용 목록읽기 명령만 통과
  3. 수정 시각파일 내용은 안 읽음
  4. 자원 상한128MB
P 문제

대시보드가 서비스를 건드리거나 큰 틱(체결) 파일을 읽어 디스크를 같이 쓰면, 수집을 지키려는 도구가 수집을 방해하게 됩니다.

A 분석
  • 명령을 내릴 수 있게 두고 조심하는 방법은 코드가 바뀔 때 깨질 수 있어 제외했습니다.
  • 명령 자체를 막는 방법을 선택해 외부 명령 실행을 한 곳에 모으고 허용 목록의 읽기 명령만 통과시켰습니다.
  • 수집이 이어지는지는 파일 내용 파싱 없이 최신 파일의 수정 시각만으로 충분하다고 판단했습니다.
A 실행
  • systemctl show, is-active, list-timers 등만 허용하고 그 밖의 명령은 예외를 내게 했습니다.
  • os.scandir로 수정 시각만 읽고 심볼릭 링크는 따라가지 않았으며, 내용을 읽어야 하는 이벤트 로그는 끝에서 최대 2MiB만 읽었습니다.
  • 수집기 서비스에 메모리 128MB, CPU 25% 상한을 걸고 배포 스크립트는 감시 유닛 5종만 등록하게 했습니다.
R 결과 코드로 확인

코드 기준으로 틱 파일 내용은 읽지 않고, 대시보드 코드로는 대상 서비스를 바꿀 수 없는 구조입니다. 자원 상한은 설정값이며 실제 사용량을 측정한 수치는 아닙니다.

한계

  • 감시 대상의 데이터와 로그가 저장소에 없고 개인 서버 구조에 맞춰져 있어 다른 환경에서 재현하기 어렵습니다.
  • 휴장일 달력은 직접 입력한 2026년 값이고, 오탐·미탐을 정량 평가하지 않았으며, 알림 기능은 없습니다.
