Port Entity Matching

항만 입출항 기록을 표준 선박 목록의 한 척으로 잇는 매칭 파이프라인

개요

DACON 항만 문제 해결 AI 대회 과제입니다. 오타가 있거나 한글로 적히고 제원이 비어 있는 입출항 기록 한 줄을, 약 7만 8천 척의 표준 선박 목록에서 맞는 선박 하나로 연결합니다. 한글 선박명이 점수의 70%를 차지해 한글 이름 매칭에 가장 공을 들였고, 교차검증 점수만 믿지 않고 교란 시나리오로 약점을 찾아 고치는 방식으로 접근했습니다.

CASE 01Port Entity Matching개인

교차검증 0.9875인데 리더보드는 0.8805였을 때, 원인을 가설로 나눠 하나씩 확인한 사례

P 문제

로컬 점수와 리더보드의 차이가 컸습니다. 원인을 모른 채 모델을 고치면 제출 기회만 낭비하므로 먼저 원인을 좁혀야 했습니다.

A 분석
  • 학습과 서빙 경로 불일치는 저장한 모델과 교차검증 예측을 비교해 차이 0건이라 제외했습니다.
  • 처음 보는 선박(정확도 0.998), 라틴 톤수 잡음(0.9965), 라틴 이름 오타(0.957)도 모두 낮은 점수를 설명하지 못해 제외했습니다.
  • 토큰 순서를 바꾸거나 하나를 빼자 정확도가 0.4~0.5로 무너졌습니다. 학습 데이터는 한 선박이 늘 같은 철자를 써서 교차검증으로는 이 변화를 볼 수 없었습니다.
A 실행
  • 깨끗한 교차검증 점수만으로 모델을 고르지 않고, 20개 교란 시나리오를 묶은 스트레스 스위트 점수를 함께 보기로 했습니다.
  • 표기 증강을 학습에 넣고, 순서에 상관없는 검색(정렬 키, 토큰 색인)과 순서 불변 특징 7종을 추가했습니다.
R 결과 백테스트

로컬 스위트 점수가 0.8162에서 0.9477로 올랐고 토큰 순서를 바꾼 라틴 이름 정확도는 0.486에서 0.999가 됐습니다. 학습 데이터로 만든 모의 교란 기준이며 실제 테스트의 교란 비율을 보여 주지는 않습니다.

CASE 02Port Entity Matching개인

규칙으로 풀기 어려운 한글 선박명을, 규칙 소리 키와 LLM 후보로 나눠 푼 사례

  1. 정규화이름 정리
  2. 후보 검색소리 키 + 톤수 창
  3. LLM 표기라틴 후보 추가
  4. 랭커LightGBM lambdarank
  5. 재순위한글 상위 10개
  6. 선박 1척vessel_id 확정
P 문제

한글 이름은 리플렉션(차용어), 흥아(로마자), 에스티아이(약어 읽기)가 섞여 표기 규칙 하나로 맞추기 어렵습니다. 한글 행은 학습 데이터의 약 9.7%지만 점수의 70%입니다.

A 분석
  • 표준 로마자 표기만 쓰면 소리 분류 키 대비 한글 오류가 24건에서 63건으로 늘어 제외했습니다.
  • 한글을 자음·모음 소리 키로 바꿔 비교하는 방식을 채택하고, 차용어 규칙(묵음 R, 어두 H, 모음 Y)을 더하자 한글 오류가 23건에서 14건으로 줄었습니다(5개 시드 평균).
  • 규칙만으로는 처음 보는 표기에 약해, LLM이 라틴 표기를 생성하는 채널을 검색 단계의 보조로 추가했습니다.
A 실행
  • 한글 소리 키와 톤수 창(±25%)으로 후보를 모으고, Kanana 1.5 2.1B가 만든 라틴 표기로도 후보를 모아 합쳤습니다.
  • LLM은 후보만 늘리고 최종 판단은 항상 랭커가 하도록 했습니다. 한글 행에는 상위 10개를 LLM 우도로 보정하는 재순위를 더했습니다.
R 결과 운영 기록

규칙 기반 v2는 공개 리더보드 0.8805였고, LLM 후보 채널을 넣은 제출은 0.9163(한글 479/532, 비한글 1701/1784)이었습니다. 표기 증강을 넣은 LLM 변형은 0.9036으로 낮아 되돌렸습니다. 공개 리더보드는 테스트의 50% 기준이며 최종 순위는 대회 종료 후 정해집니다.

CASE 03Port Entity Matching개인

손으로 정한 가중치 대신 학습형 랭커를 고르되, 차이가 불확실하다는 점도 남긴 사례

P 문제

이름 유사도, 톤수 일치, 선종 궁합 등 신호가 많고 일부는 비어 있어, 가중치를 손으로 정하면 결측을 다루기 어렵습니다.

A 분석
  • 손으로 정한 가중치 수식(점수 0.9814)과 로지스틱 회귀(0.9809)는 결측 신호를 조합하는 데 한계가 있어 제외했습니다.
  • LightGBM binary(0.9852)와 lambdarank(0.9857)를 같은 후보·같은 폴드로 비교해 후보별 순위를 직접 학습하는 lambdarank를 골랐습니다.
  • CatBoost 등과의 앙상블은 개선이 없어 채택하지 않았습니다.
A 실행
  • LightGBM lambdarank를 5개 시드 앙상블로 학습하고, 결측값은 채우지 않고 그대로 두어 모델이 처리하게 했습니다.
  • 방식 간 차이의 신뢰구간이 0을 포함한다는 사실을 문서에 그대로 적었습니다.
R 결과 백테스트

선박 단위 5-fold에서 lambdarank가 점수 0.9857로 가장 높았지만 차이는 통계적으로 확실하지 않아, 선택 이유를 성능 우위가 아니라 결측 처리의 편의로 적었습니다.

CASE 04Port Entity Matching개인

한글 선박이 382척뿐이라 흔들리는 점수를, 통계 기준으로 판단한 사례

P 문제

한글 선박 한 척이 틀리면 한글 정확도가 약 0.25%p 움직이고, 시드만 바꿔도 한글 오류가 16~19건씩 달라졌습니다. 점수 차이를 그대로 믿으면 우연을 개선으로 착각할 수 있었습니다.

A 분석
  • 한 번의 실행 결과 비교는 시드 흔들림과 구분이 안 돼 제외했습니다.
  • 선박 단위 부트스트랩 95% 신뢰구간, 5개 시드 평균, 같은 폴드 짝지은 비교를 채택했습니다.
A 실행
  • 비교 도구(tools/evaluate.py compare)를 만들고 오류 4건 미만의 차이는 한 번의 실행으로 해석하지 않는다는 기준을 문서에 남겼습니다.
  • 행 독립성(단독·일부·순서 뒤섞기에서 같은 예측)을 테스트로 강제했습니다.
R 결과 코드로 확인

15 leaves, 토큰 정렬 특징, 모델 앙상블 등 개선이 불확실한 실험은 채택하지 않았습니다.

한계

  • 로컬 점수 0.9910은 LLM 채널을 넣기 전 번들의 값이고, LLM 채널을 포함한 현재 코드의 교차검증 점수는 아직 측정하지 않았습니다. 대회 진행 중이라 최종 순위도 없습니다.
  • 토큰 하나가 빠진 이름은 아직 약하고(라틴 약 0.69, 한글 약 0.65, 모의 교란 기준), 이름과 톤수가 같은 자매선은 외부 DB를 쓸 수 없어 구분이 어렵습니다.
