Witches-Chat-Core

학사 규정을 근거 조항과 함께 답하는 온프레미스 RAG 챗봇

개요

경북대 학사 규정은 HWP·DOCX·PDF로 흩어져 있고, 클라우드 AI에는 규정과 개인정보를 보내기 어렵습니다. 학교 안에서 돌아가는 RAG 챗봇(질문과 관련된 조항을 먼저 찾아 근거로 답하는 방식)을 팀으로 만들었고, 저는 그 앞단인 규정 문서의 Markdown 변환과 구조 표시를 맡았습니다.

CASE 01Witches-Chat-Core팀

HWP·DOCX·PDF가 섞인 규정을 형식별로 처리하지 않고 Markdown 하나로 통일했다

  1. 규정 원본HWP·DOCX·PDF
  2. 형식별 변환변환기 등록
  3. 구조 표시조·항·호 기호
  4. 노이즈 정리제어문자·표
  5. 청킹 전달블록 정보 포함
P 문제

규정이 세 가지 형식으로 섞여 있고 조·항·호 계층이 의미를 정합니다. 형식마다 따로 다루면 청킹과 검색이 형식에 묶입니다.

A 분석
  • 형식별로 각각 청킹하는 방안은 팀원이 형식마다 입력을 따로 처리해야 해서 제외했습니다.
  • Markdown은 청킹 단계의 표준 입력 형식이고 제목·목록·표를 표현할 수 있어 LLM이 읽기에도 좋아 선택했습니다.
  • 팀원 모두가 같은 입력 형식을 쓸 수 있다는 점도 판단에 반영했습니다.
A 실행
  • 파일 형식별 변환기를 등록해 어떤 형식이든 같은 출력 구조를 내게 했습니다.
  • 처음에는 HWP를 DOCX로 수동 변환해 시작했고, 이후 HWP 직접 변환을 추가했습니다.
R 결과 코드로 확인

규정 원본 HWP 20·DOCX 5·PDF 4개가 Markdown 28개로 정리되어 청킹 단계로 넘어갑니다.

CASE 02Witches-Chat-Core팀

문장은 고치지 않고 조·항·호 계층 표시만 붙여 청킹이 조항 경계를 알게 했다

P 문제

조·항·호·목이 모두 같은 줄글이면 청킹 단계가 조항 경계를 몰라 조항 중간을 자를 수 있습니다.

A 분석
  • 문장을 다듬거나 요약하면 조항의 의미가 달라질 수 있어 원문 수정은 제외했습니다.
  • 원문은 그대로 두고 표시만 붙이는 방식을 선택했습니다.
A 실행
  • 줄 앞머리(제N편/장/절/관, 제N조, ①, 1., 가.)를 알아보고 제목·굵은 소제목·목록으로 표시했습니다.
  • 학칙 변환 결과에서 장·절은 제목, 조는 굵은 소제목, 항(①)과 호(1.)는 목록으로 남는 것을 확인했습니다.
R 결과 코드로 확인

계층이 Markdown 기호로 남아 청킹 단계가 읽을 수 있습니다. 단서 문장 같은 예외 조항은 별도 처리 없이 원문 순서를 그대로 둡니다.

CASE 03Witches-Chat-Core팀

의미 있는 표와 신청서 양식을 구분해 본문에서 분리했다

P 문제

규정 문서에는 신청서 서식과 빈 칸이 많은 표가 섞여 있어, 본문과 섞이면 검색 결과를 오염시키고 청킹도 어려워집니다.

A 분석
  • 표를 모두 같은 방식으로 다루면 실제 내용을 담은 표와 양식을 구분할 수 없어 제외했습니다.
  • 빈 칸 비율 같은 구조 단서와 양식 표현으로 양식을 판별하는 방식을 선택했습니다.
A 실행
  • 빈 칸이 많은 다열 표, 양식에 쓰는 표현(예: 예/아니오), 지정한 패턴이 있으면 양식으로 판별했습니다.
  • 양식은 본문과 따로 변환해 넘기고, 청킹 단계가 표를 별도 임베딩으로 처리할 수 있게 했습니다.
R 결과 코드로 확인

양식 표가 규정 본문과 분리되어 청킹 단계로 넘어갑니다. 판별 규칙의 정확도는 따로 측정하지 못했습니다.

CASE 04Witches-Chat-Core팀

DOCX·PDF 변환이 느린 원인을 라이브러리 처리 방식에서 찾아 직접 읽는 방식으로 바꿨다

P 문제

큰 규정집에서 DOCX와 PDF 변환이 느렸습니다. 변환이 느리면 규정을 고쳐 다시 변환하는 작업이 부담이 됩니다.

A 분석
  • python-docx가 단락·표를 객체로 하나씩 만드는 비용과, pymupdf4llm의 글꼴·정렬·표 영역 처리가 병목이라고 보았습니다.
  • 라이브러리를 그대로 쓰며 옵션만 조정하는 방안보다, 필요한 부분만 직접 읽는 방식을 선택했습니다.
A 실행
  • DOCX는 XML 노드(본문·표·텍스트 상자)를 직접 순회하고 제어문자는 한 번에 제거했습니다.
  • PDF는 PyMuPDF로 표 영역과 본문 글 블록을 나눠 읽었습니다.
R 결과 운영 기록

커밋 메시지에 PDF 변환이 약 70초에서 15초로 줄었다고 기록했습니다. 측정한 파일과 환경 기록은 없는 참고 수치입니다.

한계

  • 전처리 구간에는 자동 테스트가 없어, 변환 결과는 글자 수 대조 로그(85% 미만이면 경고만 남김)와 눈으로 확인했습니다.
  • 팀 전체 가드레일 결과는 직접 만든 소규모 입력 210개 기준이며 실제 사용자 질의로 평가한 것이 아닙니다. 이미지 변환은 OCR 설치 후 검증이 필요합니다.
