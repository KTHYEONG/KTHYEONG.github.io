Witches-Chat-Core

근거 조항과 함께 답하는 온프레미스 규정 RAG 챗봇

개요

규정 검색 챗봇(RAG, 검색한 문서를 근거로 답하는 방식)의 전처리로 한글(HWP)·워드(DOCX)·PDF 규정을 Markdown으로 바꾸고 조·항 구조를 표시했습니다. 학사 규정과 개인정보를 클라우드 AI에 보내기 어려워 챗봇은 학교 서버 안(온프레미스)에서 운영합니다.

  • 오피스·이미지·음성 변환 추가, 문서 쪼개기에 쓸 구간 정보를 본문에 표시해 전달

변환기 규칙 적용 결과 (Markdown)

##### 제3조의2(부총장) ① 총장의 직무를 보좌하기 위하여 교학부총장, 연구부총장, 대외협력부총장 각 1인을 두며, 교학부총장은 대학원장을 겸임한다. * ② 부총장은 아래 각호의 업무에 관하여 총장을 보좌한다. - 1 교학부총장 : 교무·학사, 학생, 입학, 정보화 등에 관한 업무 - 2 연구부총장 : 기획, 연구진흥, 산학협력, 국제교류 업무 - 3 대외협력부총장 : 대외협력 및 홍보 업무

경북대 학칙 제3조의2에 DOCX 변환기의 단락 규칙(조는 제목, 항은 목록, 호는 들여쓴 목록)을 그대로 적용해 재현한 결과이며 수정 이력 표기(<개정 …>)는 생략했습니다. PDF 변환기는 같은 구조를 굵은 조 제목 등 다른 표기로 냅니다.

CASE 01Witches-Chat-Core팀

세 가지 문서 형식을 Markdown 하나로 통일

원본 29개 파일에서 Markdown 28개(규정 24종)를 만들어 문서 쪼개기 단계에 전달했습니다.
P 문제

규정이 세 가지 파일 형식으로 섞여 있고, 조·항·호 계층이 의미를 정합니다. 형식별로 다루면 문서 쪼개기와 검색도 형식마다 따로 만들어야 합니다.

A 분석
  • 형식별 문서 쪼개기는 팀원이 형식마다 따로 처리해야 해 제외
  • Markdown은 문서 쪼개기의 표준 입력이고 제목·목록·표를 표현할 수 있어 팀원 모두 같은 입력으로 사용 가능
A 실행
  • 형식별 변환기를 두되 모두 Markdown(제목·목록·표)으로 내보내고, 구조 표시 방식은 변환기별로 다름(DOCX는 제목 5단계, PDF는 굵은 조 제목). 처음에는 HWP를 DOCX로 수동 변환하고 이후 직접 변환 추가
  • 큰 규정집은 DOCX·PDF 라이브러리 처리가 느려 XML·블록을 직접 읽는 방식으로 바꿈
R 결과

원본 29개 파일에서 Markdown 28개(규정 24종)를 만들어 문서 쪼개기 단계에 전달했습니다.

CASE 02Witches-Chat-Core팀

원문은 두고 조·항·호 계층 표시만 추가

학칙 변환 결과에서 장·절·조는 제목으로, 항·호·목은 들여쓴 목록으로 남아 문서 쪼개기 단계가 구조를 읽을 수 있습니다.
P 문제

조·항·호·목이 구분 없는 줄글이면 문서를 쪼갤 때 조항 중간이 잘려 의미가 끊길 수 있습니다. 문장을 다듬거나 요약하면 조항 의미가 달라질 수 있어, 원문은 그대로 두고 표시만 붙였습니다.

규정 계층 → Markdown 표시
  • 편 · 장 · 절 · 관→# · ## · ### · ####단계별 제목
  • 조 · 부칙 · 별표→##### 제N조(…)다섯 번째 단계 제목
  • 항 · 호 · 목→* ① / 들여쓴 - 1 / 더 들여쓴 + 가들여쓰기로 단계 표현
R 결과

학칙 변환 결과에서 장·절·조는 제목으로, 항·호·목은 들여쓴 목록으로 남아 문서 쪼개기 단계가 구조를 읽을 수 있습니다.

P 문제

신청서 서식과 빈 칸 많은 표가 본문에 섞이면 검색 결과에 불필요한 내용이 끼고 문서 쪼개기도 어렵습니다.

표 처리 방식 비교
모든 표를 같은 방식으로표 모양·양식 표현으로 판별 선택
내용 표와 양식구분할 수 없음구분해 양식만 따로 변환
검색 결과신청서 서식이 본문에 섞임규정 본문과 분리
판별 근거없음빈 칸이 있는 여러 열 표, 양식 표현(예·아니오 등), 정해 둔 글자 패턴
R 결과

CASE 04Witches-Chat-Core팀

변환 중 내용이 조용히 빠지지 않도록 점검

변환 중 내용이 크게 빠지면 경고 로그로 알 수 있고, 변환 실패는 파일마다 오류로 표시됩니다.
  1. 원본 글자 수XML·텍스트 직접 추출
  2. Markdown 변환형식별 변환기
  3. 변환 후 글자 수공백·기호 제외
  4. 비율 비교85% 미만이면 경고
  5. 로그 기록정상은 일치율 기록
P 문제

규정 변환에서 내용이 빠져도 겉으로는 알기 어렵고, 빠진 채로 검색에 쓰이면 답변의 근거가 사라집니다.

점검 방식 비교
눈으로 확인글자 수 대조 선택
누락 발견긴 규정(학칙은 공백·기호 제외 약 12만 자)에서는 놓치기 쉬움변환마다 자동으로 비율 계산
비용사람이 원본과 직접 비교변환 중 한 번 계산
알 수 있는 것보이는 부분만빠진 양(위치는 모름)
A 실행
  • 원본과 변환 결과의 글자 수를 공백·마크다운 기호를 뺀 뒤 비교하고, 85% 미만이면 경고 로그
  • DOCX·PDF·HWP·표·PPT·이미지·음성 변환기 9곳이 같은 검사를 쓰고, 변환이 실패하면 파일마다 오류로 안내
R 결과

변환 중 내용이 크게 빠지면 경고 로그로 알 수 있고, 변환 실패는 파일마다 오류로 표시됩니다.

CASE 05Witches-Chat-Core팀

블록 종류 주석으로 변환기와 쪼개기 단계 연결

여러 형식이 같은 주석 형식으로 문서 쪼개기 단계에 전달됩니다.
  1. 블록 종류 판별변환기
  2. 블록 정보 주석본문 앞에 JSON 주석
  3. 주석 읽기문서 쪼개기 단계
  4. 블록 단위 분할구간 정보 활용
P 문제

문서 쪼개기 단계는 각 조각이 제목인지 목록인지 표인지 알아야 하는데, Markdown 본문만으로는 구분이 어렵습니다.

A 실행
  • 변환기가 각 블록에 chunk:block JSON 주석을 붙여 넘기고, 문서 쪼개기 쪽이 같은 주석을 읽어 분할(형식은 팀원과 함께 정함)
  • 텍스트·엑셀·파워포인트·이미지·음성 변환도 같은 경로로 연결
R 결과

여러 형식이 같은 주석 형식으로 문서 쪼개기 단계에 전달됩니다.

한계

  • 미검증
    점검은 경고 수준전처리에는 자동 테스트가 없고, 글자 수 대조는 빠진 양만 경고합니다(중단하지 않고 변환율을 기록하지 않으며 85% 기준의 근거 기록이 없음).
  • 미검증
    구조 표시·판별 정확도정답과 대조해 측정하지 않았고, 조 제목과 제1항이 같은 줄이면 줄 전체가 제목이 되며 호 번호의 마침표가 빠집니다.
  • 해석 주의
    팀 차단율은 직접 만든 입력 기준악성 130개를 포함한 직접 만든 입력 210개 기준이라 실제 질의 평가가 아니며, 챗봇 전체의 답변 정확도 수치는 없습니다.
  • 해석 주의
    소량 문서와 속도 수치24종 규정 소량으로 확인해 속도 개선의 체감 근거가 약하고(PDF 약 70초→15초는 환경 기록 없는 커밋 메시지 기준), 이미지 변환은 OCR 설치 후 검증이 필요합니다.
