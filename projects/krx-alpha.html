KRX-Alpha

호가·체결 틱 수집·검증 데이터 파이프라인

개요

증권사 실시간 API는 끊긴 구간의 체결을 다시 보내 주지 않습니다. 알파 연구 전에 틱 수집, 누락 보충, 모의 주문 검증 인프라를 먼저 만들었습니다. 알파 연구는 시작 전입니다.

구조

사례

CASE 01KRX-Alpha개인

장중에는 받은 그대로 저장, 해석은 장 마감 후

  1. 수신실시간 시세 메시지
  2. 원본 기록받은 시각만 붙임
  3. 원본 보관압축 파일에 이어 저장
  4. 장마감 후해석·중복 제거
  5. 정리본 변환열 단위 파일 + 품질 검사
P 문제

개장 직후 시세 메시지가 한꺼번에 몰립니다. 받으면서 내용을 해석하면 처리가 밀려 일부를 놓칠 수 있습니다.

A 분석
  • 받자마자 해석: 단순하나 해석 오류가 곧 데이터 손실이라 제외
  • 원본 먼저 저장: 해석 규칙을 고쳐도 다시 계산할 수 있어 선택
A 실행
  • 수신 단계: 받은 시각만 붙여 압축 원본 파일에 이어 저장
  • 해석·중복 제거·품질 검사: 장마감 후 원본에서 정리본으로 따로 처리
R 결과

받는 단계와 해석 단계를 코드상 분리. 실제 데이터 손실률은 측정하지 않음.

CASE 02KRX-Alpha개인

끊긴 구간을 체결 번호로 찾아 타사 자료로 보충

  1. 번호 감사종목별 빈 구간 계산
  2. 구간 확정시간대·종목 특정
  3. 타사 보충키움·한국투자증권 체결 이력
  4. 병합디스크 기반 정렬
  5. 출처 표시별도 파일로 저장
P 문제

실시간 연결이 끊긴 동안의 체결 내역은 증권사가 다시 보내 주지 않아, 그대로 두면 영구히 빠집니다.

A 분석
  • 같은 증권사에 재요청: 지나간 체결은 받을 수 없어 제외
  • 타사 체결 이력 조회 사용, 먼저 빈 시간대·종목을 특정해야 함
  • 원본 보호: 보충분은 출처를 붙여 별도 저장
A 실행
  • 감사: 체결 번호가 비는 구간을 종목별로 계산
  • 보충: 키움증권·한국투자증권 체결 이력으로 빈 구간 채움
  • 병합: 디스크 기반 정렬로 합치며 중복 제거
R 결과

감사·보충·병합이 따로 실행되는 단계. 원본은 바꾸지 않음. 당일 체결만 제공하는 등 복구 불가 구간은 남을 수 있음.

CASE 03KRX-Alpha개인

백업이 확인된 파일만 삭제해 작은 디스크 운영

P 문제

임대 서버의 디스크는 작은데 틱 원본은 계속 쌓입니다. 보존 기간만 보고 지우면 백업 안 된 파일도 지워집니다.

A 분석
  • 보존 기간만으로 삭제: 업로드 실패 시 영구 손실이라 제외
  • 백업 쪽 전체 목록 조회: 느려 제외, 날짜별 파일 크기만 조회하도록 선택
A 실행
  • 구글 드라이브에 같은 크기 파일이 있고 정리까지 끝난 날짜분만 삭제
  • 디스크 여유가 3GB 미만이면 수집 중단
R 결과

업로드 미확인 날짜분은 보존 기간이 지나도 삭제 제외. 확인 시간 단축 폭은 미측정.

CASE 04KRX-Alpha개인

호가 잔량을 반영한 모의 체결, 실계좌 오주문 차단

P 문제

현재가에 전량 체결된다고 가정하면 물량 부족과 체결가 밀림을 못 봅니다. 모의용 코드가 실계좌로 나가면 사고 위험도 있습니다.

A 분석
  • 현재가에 즉시 체결: 지나치게 낙관적이라 제외
  • 10단계 호가를 유리한 쪽부터 차례로 소진: 현실에 가까워 선택
A 실행
  • 10단계 호가를 소진하며 체결가·수량 계산, 지정가 한도를 넘으면 체결 중단
  • 모든 주문이 하나의 주문 관리 시스템(OMS)과 위험 한도 검사(주문 금액·분당 주문 수·일 손실 한도·허용 종목) 통과
  • 실계좌: 실거래 허용을 명시하지 않으면 시작 단계에서 오류, 기본값은 모의
R 결과

모의·모의투자·실계좌가 같은 주문 처리부를 쓰고 실계좌만 명시 허용 필요. 모의 체결과 실제 체결의 일치 여부는 미검증.

한계

  • 전략(알파) 단계 없음: 신호 생성·백테스트 엔진·수익 수치 없음
  • 틱 손실 0 아님: 복구 불가 구간 가능, 모의 체결 현실성 미검증
