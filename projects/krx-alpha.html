KRX-Alpha

국내주식 호가·체결 틱을 모으고 검증하는 데이터 파이프라인

개요

단기투자 전략 백테스트는 데이터에 구멍이 있으면 쉽게 틀어지는데, 증권사 실시간 API는 연결이 끊긴 구간의 체결을 다시 보내 주지 않습니다. 그래서 전략(알파) 연구에 앞서 호가·체결 틱을 빠짐없이 모으고, 빈 곳을 찾아 메우고, 모의 주문을 검증하는 인프라를 먼저 만들었습니다. 알파 연구 단계는 아직 시작 전이며, 이 프로젝트는 수집·검증·모의 집행까지가 범위입니다.

CASE 01KRX-Alpha개인

개장 직후 메시지 폭주에도 놓치지 않도록, 장중에는 파싱하지 않고 원본만 기록했다

  1. 수신WebSocket 메시지
  2. 원본 기록recv_ts만 붙임
  3. L0 보관jsonl.zst 이어쓰기
  4. 장마감 후파싱·중복 제거
  5. L1 변환Parquet + 품질 검사
P 문제

개장 직후에는 초당 메시지가 몰립니다. 수신 중에 파싱·검증까지 하면 처리가 밀려 메시지를 놓칠 수 있습니다.

A 분석
  • 수신하며 바로 정제하는 방식은 구현이 단순하지만, 파싱 오류가 곧 데이터 손실이 되어 제외했습니다.
  • 원본을 먼저 남기는 방식은 나중에 규칙을 고쳐도 다시 계산할 수 있어 선택했습니다.
A 실행
  • 수신 경로는 받은 메시지에 수신 시각(recv_ts)만 붙여 압축 파일(.jsonl.zst)에 이어 쓰기만 하도록 했습니다.
  • 파싱·중복 제거·품질 검사는 장마감 후 정규화 단계(L0 원본 → L1 Parquet)로 분리했습니다.
R 결과 코드로 확인

수신 경로와 해석 단계가 코드상 분리되어 있습니다. 실제 손실률은 측정해 기록하지 않았습니다.

CASE 02KRX-Alpha개인

연결이 끊긴 구간의 체결을 순번으로 찾아 다른 증권사 API로 보충했다

  1. 순번 감사종목별 빈틈 계산
  2. 구간 확정시간대·종목 특정
  3. 타사 보충키움·KIS 체결 이력
  4. 병합SQLite 외부 정렬
  5. 출처 표시별도 파일로 저장
P 문제

수신 지연이 커지다 연결이 끊기면 그 구간의 체결은 증권사가 다시 보내 주지 않아 영구히 빠집니다.

A 분석
  • 같은 증권사에 다시 요청해도 이미 지나간 체결은 받을 수 없어 제외했습니다.
  • 다른 증권사의 체결 이력 API로 채우되, 어느 시간대·종목이 비었는지 먼저 정확히 알아야 한다고 판단했습니다.
  • 원본을 고치지 않도록, 보충분은 출처(vendor, provenance)를 붙인 별도 파일로만 쌓았습니다.
A 실행
  • 틱마다 붙은 체결 순번의 빈틈을 종목별로 계산하는 감사 단계를 만들었습니다.
  • 키움증권 체결 이력과 한국투자증권 API로 빈 구간을 채우는 보충 단계를 만들었습니다.
  • 원본과 보충분을 SQLite 외부 정렬로 합치며 중복을 제거하는 병합 단계를 만들었습니다.
R 결과 코드로 확인

감사 → 보충 → 병합이 각각 독립된 CLI 단계로 나뉘어 있고, L0 원본은 건드리지 않습니다. 증권사가 당일 체결만 제공하는 등 복구할 수 없는 구간은 남을 수 있습니다.

CASE 03KRX-Alpha개인

작은 디스크에서 백업이 확인된 파일만 지우도록 했다

P 문제

틱 원본은 하루에도 크게 쌓이는데 VPS 디스크는 작습니다. 보존 기간만 보고 지우면 업로드가 덜 된 파일까지 지울 수 있습니다.

A 분석
  • 보존 기간만으로 삭제하는 방식은 업로드 실패 시 영구 손실이 생겨 제외했습니다.
  • 원격 전체 목록을 매번 훑는 방식은 느려 제외하고, 날짜별 접두사로 파일 크기를 하나씩 조회하는 방식을 선택했습니다.
A 실행
  • 원격(Google Drive)에 같은 크기의 파일이 있고 정규화가 끝난 파티션만 로컬에서 삭제하도록 했습니다.
  • 여유 공간이 3 GB 아래로 내려가면 수집을 멈추는 장치(min_free_disk_gb)를 두었습니다.
R 결과 코드로 확인

업로드 확인이 안 된 파티션은 보존 기간이 지나도 삭제 대상에서 제외됩니다. 대사 시간 단축 폭은 측정하지 않았습니다.

CASE 04KRX-Alpha개인

모의 주문이 호가 잔량을 반영하고, 실계좌로는 실수로 나가지 않게 막았다

P 문제

모의 매매에서 '현재가에 전량 체결'로 가정하면 호가 잔량 부족과 슬리피지(체결가 차이)를 확인할 수 없습니다. 반대로 같은 코드가 실계좌 주문까지 낼 수 있으면 사고 위험이 있습니다.

A 분석
  • 현재가 즉시 체결은 단순하지만 낙관적이어서 제외했습니다.
  • 10단계 호가를 위에서부터 소진하는 방식이 더 현실에 가까워 선택했습니다.
A 실행
  • 10호가를 소진하며 체결가와 수량을 계산하고, 지정가는 한도를 넘으면 멈추도록 했습니다.
  • 모든 주문이 하나의 OMS와 사전 리스크 게이트(주문 금액·분당 주문 수·일 손실 한도·종목 화이트리스트)를 거치게 했습니다.
  • 실계좌 모드는 KRX_ALPHA_EXEC_LIVE_ARMED=true가 없으면 설정 단계에서 오류가 나게 하고, 기본값은 모의로 두었습니다.
R 결과 코드로 확인

모의·모의투자·실계좌 세 모드가 같은 OMS를 쓰고 실계좌만 명시적 허용이 필요합니다. 실계좌 운용은 하지 않았고, 모의 체결이 실제와 얼마나 맞는지는 아직 검증하지 않았습니다.

한계

  • 전략(알파) 단계가 없습니다. 신호 생성과 백테스트 엔진은 이 저장소에 없고, 수익 성과 수치도 없습니다.
  • 틱 손실이 0은 아닙니다. 보충 API로 복구할 수 없는 구간이 있을 수 있고, 모의 체결 현실성도 실제 체결과 비교하지 않았습니다.
