경북대학교 컴퓨터학부 · 2027.02 졸업 예정

김태형TaeHyeong Kim

투자 전략과 데이터 시스템을 처음부터 끝까지 만들어 본 신입 개발자

금융 데이터로 가설을 세우고, 비용과 시차까지 넣어 검증하고, 그 결과를 실제로 매일 도는 시스템으로 옮기는 일을 개인 프로젝트로 반복해 왔습니다. 좋은 수익률보다 "이 숫자를 믿어도 되는가"를 먼저 묻는 편이고, 검증하지 못한 것은 성과로 쓰지 않습니다.

  • 미래 정보를 쓰지 않는다

    의사결정 시각에 알 수 있던 데이터만 쓰도록 데이터와 코드의 경계를 분리합니다.

  • 비용을 먼저 반영한다

    거래세·호가 단위·슬리피지처럼 수익을 깎는 요소를 백테스트가 끝난 뒤가 아니라 종목 선별 단계에서 다룹니다.

  • 이상하면 멈춘다

    데이터가 의심스러울 때 임의로 보정하지 않고 실행을 중단하는(Fail-Closed) 쪽을 기본값으로 둡니다.

전략을 비용까지 넣어 검증하고, 체결과 리스크를 원장으로 재현해 봤습니다

국내 종가매매, 암호화폐 선물, ETF 투자대회에서 같은 순서를 반복했습니다. 판단 시각에 알 수 있는 정보만 쓰고, 호가·세금·수수료를 반영해 검증하고, 여러 번 시험한 편향까지 보정했습니다. 수익률보다 "이 숫자를 믿어도 되는가"를 먼저 따졌습니다.

문제 해결 사례

CASE 01K-Closing Alpha개인

1틱 비용이 12bp를 넘는 종목을 순위 매기기 전에 제외해 비용에 지는 매매를 걸러냈다

P 문제

점수 상위 종목을 그대로 사면 호가 간격이 큰 저가주가 많이 들어옵니다. 1틱이 가격의 20~50bp인 종목은 세금과 슬리피지를 빼면 손실이 납니다.

A 분석
  • 상한을 6, 9, 12, 15bp와 상한 없음으로 바꿔 비교했습니다.
  • 15bp는 Sharpe가 2.88로 더 높지만 매매가 이뤄진 날이 83.3%로 12bp의 99.7%보다 적어 제외했습니다.
  • 12bp는 후보 종목 수를 7.5bp 대비 2.6배로 늘리면서 Sharpe도 높아 선택했습니다.
A 실행
  • 가격대별 호가 단위 표를 코드에 넣고 1틱 / 현재가를 계산해 12bp 초과 종목을 제외했습니다.
  • 거래세는 날짜별 세율표로, 수수료는 적용받는 증권사 우대율(왕복 약 0.73bp)로 반영했습니다.
  • 상한가 근처 종목 처리도 같은 전략 계약 안에 두었습니다.
R 결과 백테스트

5,000원 미만 종목만 사면 일평균 -12.53bp, 5,000~20,000원 구간은 +24.02bp였습니다(백테스트, 연구 문서 4절).

CASE 02K-Closing Alpha개인

겹치는 라벨을 제거한 CPCV와 교체 게이트로, 우연히 좋은 모델이 운영에 들어가는 길을 막았다

  1. 8구간 분할2구간을 시험용
  2. 앞뒤 제외시험 구간 인접 1구간
  3. 28개 분할독립 경로 7개
  4. 주간 재학습신규 모델 생성
  5. 교체 게이트순위 일치도 0.95 이상
P 문제

라벨 기간이 겹치는 데이터를 무작위로 나누면 학습과 평가가 섞입니다. 118개 전략을 비교하면 우연히 좋은 전략을 고를 위험도 있습니다.

A 분석
  • 단순 시간 분할은 평가 경로가 한 개뿐이라 한 번의 운에 좌우되어 제외했습니다.
  • 데이터를 8구간으로 나눠 2구간을 시험용으로 뽑는 조합 방식(CPCV)은 평가 경로를 여러 개 만들어 선택했습니다.
A 실행
  • CPCV(8, 2)로 28개 분할(독립 경로 7개)을 만들고, 시험 구간 앞뒤 1구간씩을 학습에서 뺐습니다.
  • 매주 재학습한 모델은 최근 20거래일 예측 순위 일치도 0.95 이상 등의 기준을 통과해야 운영 모델이 되도록 게이트를 만들었습니다.
R 결과 코드로 확인

기준 미달 모델은 운영에 올라가지 못하는 구조를 갖췄습니다. 다만 118개 중 고른 결과라 선택 편향은 남아 있고, 보정 결과는 제시하지 않았습니다.

CASE 03Crypto Pilot개인

수익 극대화 대신 강제청산 규칙을 넣은 계좌 시뮬레이션으로 레버리지 정하기

  1. 수익 분포시점별 갱신
  2. 배율 선택기대 성장 최대
  3. 상한 적용10배·증거금 90%
  4. 계좌 시뮬유지증거금·펀딩비
  5. 청산 확인강제청산 여부
P 문제

같은 신호도 레버리지를 높이면 수익이 커 보이지만, 급락 때 유지증거금(포지션 유지에 필요한 최소 증거금)이 모자라면 강제청산됩니다. 비중만 계산하는 백테스트는 이 위험과 최소 주문 수량 때문에 거절되는 주문을 반영하지 못합니다.

A 분석
  • 전체 기간 수익률을 보고 고정 배율을 고르면 미래 정보를 쓴 셈이라 제외했습니다.
  • 과거 수익만으로 매일 배율을 다시 정하는 방식은 그 시점에 알 수 있는 정보만 쓰므로 선택했습니다.
  • 배율을 정하는 것과 별개로, 증거금 규칙을 넣은 계좌 시뮬레이터가 있어야 청산 여부를 확인할 수 있다고 판단했습니다.
A 실행
  • 신호 수익률 분포를 시점마다 갱신해 기대 로그 성장이 가장 큰 배율을 고르고, 상한 10배와 증거금 한도(초기 증거금의 90%)를 두었습니다.
  • 심볼별 유지증거금 구간, 펀딩비, 수수료, 최소 주문 단위를 반영하는 계좌 시뮬레이터를 구현했습니다.
R 결과 재현 시뮬레이션

재현 시뮬레이션($1,000, 2021-04 ~ 2026-10)에서 강제청산 0회, MDD -51.2%였습니다. 평균 배율이 약 3.8배라 낙폭이 커서 실제 운용에서 버티기 어려운 수준이라는 점도 한계로 적어 두었습니다.

CASE 04Crypto Pilot개인

종가 체결 가정 대신 3분봉으로 지정가 체결을 재현하기

  1. 주문 발생지정가 주문
  2. 3분봉 순회30분 구간
  3. 체결 판정지나간 만큼만
  4. 월 단위 이월보유·대기 주문
  5. 동치 검증전체 처리와 비교
P 문제

1시간봉 종가에 바로 체결된다고 가정하면 수수료, 호가 차이, 지정가 미체결이 모두 빠져 실제와 결과가 달라집니다.

A 분석
  • 시장가(테이커)는 체결이 확실하지만 수수료가 높아(이 프로젝트 설정 6bp, 1bp=0.01%) 제외했습니다.
  • 지정가(메이커)는 수수료가 낮지만(2bp) 체결이 안 될 수 있어, 체결 여부를 가격 경로로 판정해야 했습니다.
  • 5.25년치 3분봉을 한 번에 올리면 메모리가 부족해, 월 단위로 나눠 처리하되 결과는 한 번에 처리한 것과 같아야 한다고 정했습니다.
A 실행
  • 주문 시점 이후 3분봉 10개 구간(30분) 동안 가격이 지정가를 지나간 만큼만 체결로 인정하는 집행 시뮬레이터를 구현했습니다.
  • 월 단위로 읽으며 보유 수량과 대기 주문을 다음 구간으로 넘기도록 했습니다.
  • 월 단위 처리 결과와 전체 한 번에 처리한 결과가 같은지 동치 테스트로 확인합니다.
R 결과 코드로 확인

지정가 중심 집행으로 정하고 이를 계좌 시뮬레이션의 기본 집행 방식으로 썼습니다. 월 단위 처리가 전체 처리와 같은 결과를 내는지는 테스트로 검증합니다.

CASE 05MT ETF King 2026개인

급락 직후 현금 도피로 반등을 놓치는 문제를 반등 앵커 규칙으로 보완한 과정

P 문제

기본 전략은 60일 모멘텀이 마이너스면 현금으로 빠져, 폭락 직후 첫 반등을 놓칠 수 있습니다. 8주 안에 큰 수익을 노리는 대회에서는 이 비용이 큽니다.

A 분석
  • 반등을 매번 따라 사는 방식은 하락장에서 손실이 커져 제외했습니다.
  • 60일 모멘텀이 음수여도 20일 모멘텀이 양전환할 때만 지정 종목을 사고, 고점 대비 15% 하락 시 손절하는 조건부 규칙을 선택했습니다.
  • 같은 기초지수의 1배·2배·인버스를 함께 담으면 사실상 중복이므로 한 묶음으로 보고 한 종목만 담게 했습니다.
A 실행

문제 해결 사례

CASE 01KRX-Alpha개인

개장 직후 메시지 폭주에도 놓치지 않도록, 장중에는 파싱하지 않고 원본만 기록했다

  1. 수신WebSocket 메시지
  2. 원본 기록recv_ts만 붙임
  3. L0 보관jsonl.zst 이어쓰기
  4. 장마감 후파싱·중복 제거
  5. L1 변환Parquet + 품질 검사
P 문제

개장 직후에는 초당 메시지가 몰립니다. 수신 중에 파싱·검증까지 하면 처리가 밀려 메시지를 놓칠 수 있습니다.

A 분석
  • 수신하며 바로 정제하는 방식은 구현이 단순하지만, 파싱 오류가 곧 데이터 손실이 되어 제외했습니다.
  • 원본을 먼저 남기는 방식은 나중에 규칙을 고쳐도 다시 계산할 수 있어 선택했습니다.
A 실행
  • 수신 경로는 받은 메시지에 수신 시각(recv_ts)만 붙여 압축 파일(.jsonl.zst)에 이어 쓰기만 하도록 했습니다.
  • 파싱·중복 제거·품질 검사는 장마감 후 정규화 단계(L0 원본 → L1 Parquet)로 분리했습니다.
R 결과 코드로 확인

수신 경로와 해석 단계가 코드상 분리되어 있습니다. 실제 손실률은 측정해 기록하지 않았습니다.

CASE 02KRX-Alpha개인

연결이 끊긴 구간의 체결을 순번으로 찾아 다른 증권사 API로 보충했다

  1. 순번 감사종목별 빈틈 계산
  2. 구간 확정시간대·종목 특정
  3. 타사 보충키움·KIS 체결 이력
  4. 병합SQLite 외부 정렬
  5. 출처 표시별도 파일로 저장
P 문제

수신 지연이 커지다 연결이 끊기면 그 구간의 체결은 증권사가 다시 보내 주지 않아 영구히 빠집니다.

A 분석
  • 같은 증권사에 다시 요청해도 이미 지나간 체결은 받을 수 없어 제외했습니다.
  • 다른 증권사의 체결 이력 API로 채우되, 어느 시간대·종목이 비었는지 먼저 정확히 알아야 한다고 판단했습니다.
  • 원본을 고치지 않도록, 보충분은 출처(vendor, provenance)를 붙인 별도 파일로만 쌓았습니다.
A 실행
  • 틱마다 붙은 체결 순번의 빈틈을 종목별로 계산하는 감사 단계를 만들었습니다.
  • 키움증권 체결 이력과 한국투자증권 API로 빈 구간을 채우는 보충 단계를 만들었습니다.
  • 원본과 보충분을 SQLite 외부 정렬로 합치며 중복을 제거하는 병합 단계를 만들었습니다.
R 결과 코드로 확인

감사 → 보충 → 병합이 각각 독립된 CLI 단계로 나뉘어 있고, L0 원본은 건드리지 않습니다. 증권사가 당일 체결만 제공하는 등 복구할 수 없는 구간은 남을 수 있습니다.

CASE 03K-Closing Alpha개인

주문을 보내기 전에 먼저 기록하고, 응답이 불확실하면 증권사 원장으로 확인해 중복 주문을 막았다

  1. 의도 기록INTENT 디스크 저장
  2. 주문 전송SEND 기록
  3. 응답 불확실UNKNOWN 상태
  4. 원장 조회같은 주문 탐색
  5. 채택/종결ADOPT 또는 종결
P 문제

주문 응답이 타임아웃되면 접수 여부를 알 수 없습니다. 그대로 재전송하면 이중 매수가 됩니다.

A 분석
  • 재시도 횟수를 제한하는 방법은 이미 접수된 주문을 막지 못해 제외했습니다.
  • 보내기 전에 기록을 남기고, 결과가 불확실하면 증권사 원장을 조회해 맞추는 방식을 선택했습니다.
A 실행
  • 주문 의도(INTENT)와 전송(SEND)을 디스크에 먼저 쓰고 전송했습니다.
  • 응답이 불확실하면 UNKNOWN 상태로 두고, 원장에서 같은 주문을 찾으면 채택(ADOPT), 없을 때만 종결하도록 했습니다.
  • 종가는 시각, 장운영 구분코드, 현재가와 호가 조회 가격 일치의 3조건을 모두 만족할 때만 확정합니다.
R 결과 코드로 확인

상태 전이와 채택 로직, 종가 확정 조건 함수를 구현했고 단위 테스트가 있습니다. 실거래 운영 기록은 없습니다.

CASE 04SaveTax개인

같은 주문이 여러 물품에 중복돼 합계가 부풀려지는 문제를, 불일치는 멈추는 방식으로 풀기

  1. 로드Parquet 직접 조회
  2. 무결성 검사dlv_key별 일치 확인
  3. 불일치 중단오류로 멈춤
  4. 정규화 뷰주문당 1건
  5. 집계빈 값은 0 아님
P 문제

같은 주문 기록(dlv_key)이 여러 물품 아래에 반복돼, 단순 합계가 실제보다 큽니다. 집계 기준이 틀리면 이후의 모든 후보 판정이 어긋납니다.

A 분석
  • 합계 전에 중복을 없애야 하지만, 묶은 기록끼리 계약번호나 금액이 다르면 합치면 안 됩니다.
  • 주문이 없는 물품(약 71%)은 값이 비어 있는 것이지 0이 아니므로, 0으로 채우면 평균이 왜곡돼 제외했습니다.
  • 불일치를 조용히 넘기는 것보다, 데이터를 불러오는 시점에 멈추는 쪽을 선택했습니다.
A 실행
  • DuckDB로 Parquet을 직접 조회하며 dlv_key별 계약번호·금액이 하나로 일치하는지 검사합니다.
  • 주문당 한 건으로 집계하는 정규화 뷰를 만들고, 불일치하면 오류로 중단합니다.
  • 빈 값은 0으로 바꾸지 않고 그대로 둡니다.
R 결과 코드로 확인

주문당 한 건으로 집계하는 뷰를 쓰고, 불일치 데이터는 조용히 넘어가지 않고 중단됩니다. 약 24%라는 수치는 대회 데이터 안내의 값입니다.

CASE 05Port Entity Matching개인

교차검증 0.9875인데 리더보드는 0.8805였을 때, 원인을 가설로 나눠 하나씩 확인한 사례

P 문제

로컬 점수와 리더보드의 차이가 컸습니다. 원인을 모른 채 모델을 고치면 제출 기회만 낭비하므로 먼저 원인을 좁혀야 했습니다.

A 분석
  • 학습과 서빙 경로 불일치는 저장한 모델과 교차검증 예측을 비교해 차이 0건이라 제외했습니다.
  • 처음 보는 선박(정확도 0.998), 라틴 톤수 잡음(0.9965), 라틴 이름 오타(0.957)도 모두 낮은 점수를 설명하지 못해 제외했습니다.
  • 토큰 순서를 바꾸거나 하나를 빼자 정확도가 0.4~0.5로 무너졌습니다. 학습 데이터는 한 선박이 늘 같은 철자를 써서 교차검증으로는 이 변화를 볼 수 없었습니다.
A 실행
  • 깨끗한 교차검증 점수만으로 모델을 고르지 않고, 20개 교란 시나리오를 묶은 스트레스 스위트 점수를 함께 보기로 했습니다.

CASE 01Emori팀

규칙 템플릿도, 범용 LLM도 아닌 파인튜닝을 선택한 이유

  1. 원본 통합뇌파·VR TXT를 JSON으로
  2. 증강규칙 기반 50세트
  3. 정답 작성4문체 280개
  4. LoRA 학습Llama 3.1 8B
  5. 리포트서술형 요약 생성
P 문제

뇌파 지표는 숫자라 상담자가 바로 읽기 어려워, 협력 기업과 협의해 정해진 형식에 가까운 서술형 답변을 만드는 방향으로 정했습니다.

A 분석
  • 규칙 기반 템플릿은 문장이 반복적이고 지표를 하나씩만 해석해, 여러 지표가 함께 움직이는 패턴을 못 담아 제외했습니다.
  • LLM을 그대로 호출하면 도메인 표현이 부족하고 일반적인 말만 해서 제외했습니다.
  • 학습 가능한 데이터가 100개 이하라, 파인튜닝에 데이터 증강과 여러 문체의 정답을 결합하기로 했습니다.
A 실행
  • Llama 3.1 8B Instruct를 4비트(NF4) 양자화하고 LoRA(r=32, alpha=16, 대상 q_proj/v_proj)로 학습했습니다.
  • 에폭 7, 배치 1 x 누적 8, 학습률 3e-4(cosine)로 개인 PC(RTX 4070 Ti)에서 학습했습니다.
  • 변환부터 요약 생성까지 한 번에 실행하는 파이프라인을 구성했습니다.
R 결과 코드로 확인

체험 시작, 중간, 마지막 3단계를 각각 한 문장으로 서술하는 요약이 생성됩니다. 정량 평가는 하지 않았고 생성 문장을 직접 읽어 확인했습니다.

P 문제

제공받은 학생 데이터가 적어 증강이 필요했습니다.

A 분석
  • 단순 무작위 생성은 스트레스와 이완이 함께 높은 식의 비현실적인 조합을 만들어 제외했습니다.
  • 정서 이론(러셀의 감정 이론 등)을 처음 공부하며 참고해, 지표 간 관계를 반영하는 규칙을 직접 정했습니다.
A 실행
  • 처음 9세트는 제공받은 기록의 흐름을 유지하고, 나머지는 +-20% 범위에서 생성했습니다.
  • 스트레스는 이완의 반대 방향으로 만들고, 서로 어긋나는 극단 조합의 빈도를 제한했습니다.
  • 시드를 고정해 재현할 수 있게 했고, 코드와 단어표의 값 이름(Full/Half/Low 등)을 원본 기준으로 통일해 증강 JSON을 다시 만들었습니다.
R 결과 코드로 확인

50세트를 생성했고 감정 종류와 강도 값이 모두 단어표에 있는 값임을 확인했습니다. 실제 사람 데이터와의 유사도는 검증하지 못했습니다.

HWP·DOCX·PDF가 섞인 규정을 형식별로 처리하지 않고 Markdown 하나로 통일했다

  1. 규정 원본HWP·DOCX·PDF

규정이 세 가지 형식으로 섞여 있고 조·항·호 계층이 의미를 정합니다. 형식마다 따로 다루면 청킹과 검색이 형식에 묶입니다.

A 분석
  • 형식별로 각각 청킹하는 방안은 팀원이 형식마다 입력을 따로 처리해야 해서 제외했습니다.

  • 팀원 모두가 같은 입력 형식을 쓸 수 있다는 점도 판단에 반영했습니다.
A 실행
  • 파일 형식별 변환기를 등록해 어떤 형식이든 같은 출력 구조를 내게 했습니다.
  • 처음에는 HWP를 DOCX로 수동 변환해 시작했고, 이후 HWP 직접 변환을 추가했습니다.
R 결과 코드로 확인

규정 원본 HWP 20·DOCX 5·PDF 4개가 Markdown 28개로 정리되어 청킹 단계로 넘어갑니다.

CASE 04Witches-Chat-Core팀

의미 있는 표와 신청서 양식을 구분해 본문에서 분리했다

P 문제

규정 문서에는 신청서 서식과 빈 칸이 많은 표가 섞여 있어, 본문과 섞이면 검색 결과를 오염시키고 청킹도 어려워집니다.

A 분석
  • 표를 모두 같은 방식으로 다루면 실제 내용을 담은 표와 양식을 구분할 수 없어 제외했습니다.
  • 빈 칸 비율 같은 구조 단서와 양식 표현으로 양식을 판별하는 방식을 선택했습니다.
A 실행
  • 빈 칸이 많은 다열 표, 양식에 쓰는 표현(예: 예/아니오), 지정한 패턴이 있으면 양식으로 판별했습니다.
  • 양식은 본문과 따로 변환해 넘기고, 청킹 단계가 표를 별도 임베딩으로 처리할 수 있게 했습니다.
R 결과 코드로 확인

양식 표가 규정 본문과 분리되어 청킹 단계로 넘어갑니다. 판별 규칙의 정확도는 따로 측정하지 못했습니다.

CASE 05Port Entity Matching개인

규칙으로 풀기 어려운 한글 선박명을, 규칙 소리 키와 LLM 후보로 나눠 푼 사례

  1. 정규화이름 정리
  2. 후보 검색소리 키 + 톤수 창
  3. LLM 표기라틴 후보 추가
  4. 랭커LightGBM lambdarank
  5. 재순위한글 상위 10개
  6. 선박 1척vessel_id 확정
P 문제

한글 이름은 리플렉션(차용어), 흥아(로마자), 에스티아이(약어 읽기)가 섞여 표기 규칙 하나로 맞추기 어렵습니다. 한글 행은 학습 데이터의 약 9.7%지만 점수의 70%입니다.

A 분석
  • 표준 로마자 표기만 쓰면 소리 분류 키 대비 한글 오류가 24건에서 63건으로 늘어 제외했습니다.
  • 한글을 자음·모음 소리 키로 바꿔 비교하는 방식을 채택하고, 차용어 규칙(묵음 R, 어두 H, 모음 Y)을 더하자 한글 오류가 23건에서 14건으로 줄었습니다(5개 시드 평균).
  • 규칙만으로는 처음 보는 표기에 약해, LLM이 라틴 표기를 생성하는 채널을 검색 단계의 보조로 추가했습니다.
A 실행
  • 한글 소리 키와 톤수 창(±25%)으로 후보를 모으고, Kanana 1.5 2.1B가 만든 라틴 표기로도 후보를 모아 합쳤습니다.
  • LLM은 후보만 늘리고 최종 판단은 항상 랭커가 하도록 했습니다. 한글 행에는 상위 10개를 LLM 우도로 보정하는 재순위를 더했습니다.
